# Умный дисплей — выжимка архитектурных решений

## Идея и позиционирование

Кастомный информационный дисплей с открытой экосистемой. Главный девиз — **свобода**: пользователь сам выбирает эстетику (пиксельную, минималистичную, насыщенную), сам собирает экран из готовых объектов как в Фотошопе, и при желании пишет скрипты.

Ниша: между закрытым Divoom/Pixoo (мало свободы) и AWTRIX (много свободы, но спартанский UI). Уникальность — **визуальный редактор**, которого нет ни у кого.

---

## Железо

| Решение | Обоснование |
|---|---|
| **Обычный IPS/OLED дисплей**, не LED матрица | Пиксельную эстетику можно сделать программно; обратное невозможно |
| **Raspberry Pi Zero 2W** как основа | Linux, нормальный HTTP стек, QuickJS, запуск за 4–8 сек с оптимизацией |
| STM32 Nucleo + OLED + dot matrix | Первый прототип для валидации идеи и рендерера |
| ESP32 | Рассматривался, ограничен для полноценного рантайма |

Форм-фактор: квадратный или широкоформатный (не вытянутый), больше Pixoo Max по диагонали.

---

## Прошивка

**Язык: Rust**

- Рендерер — горячий путь, Rust исключает buffer overflow на этапе компиляции
- `embassy-rs` даёт async/await на bare metal без OS
- `serde` + `#[derive(Deserialize)]` — парсинг и валидация JSON бесплатно
- `core` крейт (типы, рендерер) тестируется на десктопе через `cargo test`, рендер в PNG

**Структура крейтов:**
```
core/     — типы, рендерер, интерполятор (платформонезависимо)
platform/ — HAL, дисплей, Wi-Fi, HTTP
```

## Архитектура системы

```
[Веб-редактор]  ←→  [JSON конфиг]  →  [Устройство]
                                           ├── DataSources (HTTP pull)
                                           ├── Variables store
                                           ├── Template renderer
                                           └── Framebuffer → Дисплей
```

Устройство — не браузер. Это **template renderer**: цикл который подставляет переменные в шаблон, вычисляет трансформы и анимации, рисует в framebuffer. Принципиально проще браузера — нет DOM, нет reflow, нет layout engine.

Синхронизация двусторонняя: устройство отдаёт heartbeat с текущим состоянием, редактор показывает live preview реального устройства.

Транспорт: **JSON over HTTP** (`PUT device.local/config`). Protobuf отложен — преждевременная оптимизация пока контракт итерируется.

## Модель данных

### Иерархия
```
Screen
  └── Scene  (набор слоёв + правила переключения)
        └── Layer  (Text | Image | Shape | Canvas | Video)
              ├── Transform  (x, y, w, h, opacity, scale, z)
              ├── Source     (static | binding | template)
              └── Animation  (keyframes на любое свойство)

DataSources  (Spotify, Weather, HTTP, System)
  └── Variables  — доступны слоям через {{name}}
```

### Атомы на разных уровнях
- **Для пользователя** → Layer (высокоуровневый объект, как в Фотошопе)
- **Для рендерера** → Pixel во framebuffer
- Layer — это абстракция; рендерер внутри всё равно работает с пикселями

---

## Типы слоёв

| Тип | Описание |
|---|---|
| **Text** | Строка, шрифт (enum встроенных bitmap шрифтов), overflow: clip/scroll/wrap |
| **Image** | URL или base64; источник — статика или binding (обложка трека) |
| **Shape** | Прямоугольник, круг, линия; параметры через переменные |
| **Canvas** | Программируемая поверхность; скрипт на QuickJS |
| **Video** | Делегирует декодирование ffmpeg/gstreamer; композитится как слой |

### Source на слое
```json
{ "static": "Hello" }
{ "binding": "spotify.track.title" }
{ "template": "{{artist}} — {{title}}" }
```

DataSources опрашиваются по расписанию, результат кладётся в Variables. Слои только читают Variables — сами ничего не тянут. Рендерер работает синхронно.

---

## Анимация

Keyframes с нормализованным временем `t: 0..1`. Easing задаётся на каждом keyframe отдельно и описывает кривую до следующей точки.

Анимируемые свойства: `opacity`, `transform.x/y/scale`.

Триггеры:
- `onEnter` — при входе в сцену
- `onExit` — при выходе
- `onDataChange` — когда изменилась переменная в source
- `always` — каждый кадр

`duration` и keyframes разделены — скорость меняется одним полем, пропорции сохраняются.

## Canvas слой и скрипты

Рантайм: **QuickJS** (встраиваемый JS, ~200KB, Rust биндинги `quickjs-rs`).

Данные в скрипт попадают только через поле `vars` — список переменных из DataSources инжектируется как глобальные. Скрипт не делает HTTP запросов, не трогает filesystem, не использует таймеры (ритм задаётся через `script.fps` и `time.now()`).

Изоляция реализуется на уровне того, что инжектируется в контекст QuickJS — ничего лишнего.

Canvas — единственная точка где пользователь спускается до уровня пикселей. Обычный пользователь Canvas не трогает.

## Редактор

- Базово: drag & drop (Layer как объект с ручками)
- При необходимости: встроенный код-редактор (для Canvas слоя)
- Live preview: либо эмулятор в браузере, либо отображение реального устройства через heartbeat
- Открывается по `device.local` в браузере с телефона или ПК
- Разрешение экрана определяется автоматически при подключении

## Граница свободы

Абсолютная свобода (рабочий стол, произвольное видео) — это просто Linux, и там продукт заканчивается. Граница осознанная:

```
Text / Image / Shape  →  редактор без кода
Canvas + скрипт       →  максимум внутри системы
Linux / framebuffer   →  за пределами продукта
```

Video слой укладывается в архитектуру: рендерер делегирует декодирование, получает кадры, композитит вместе с остальными слоями.

## Абстракция экрана

**Принцип: любой дисплей, только зная его размеры.**

Для рендерера `core` экран — это просто `&mut [u8]`, плоский framebuffer. Всё что связано с физическим выводом — в `platform` крейте. Рендереру всё равно какой интерфейс используется.

### Device manifest

При подключении устройство отдаёт манифест — редактор читает его и подстраивает canvas:

```json
{
  "device": {
    "name": "my-display",
    "firmware": "0.1.0",
    "screen": {
      "w": 480,
      "h": 480,
      "dpi": 218,
      "interface": "spi"
    }
  }
}
```

Поле `interface` — `"spi"` | `"hdmi"` | `"rgb_parallel"` | `"mipi_dsi"`. Пользователь указывает его один раз при настройке прошивки. Редактор это поле не видит и не использует.

Все координаты в JSON конфиге — в реальных пикселях экрана. Никакой нормализации и процентов: что видишь в редакторе, то и на экране.

### Открытый вопрос: шрифты и dpi

480×480 при 2" и 480×480 при 5" — очень разный результат для bitmap шрифтов. Варианты:
- Хранить несколько размеров растеризованных шрифтов (просто, но раздувает прошивку)
- Векторные шрифты с растеризацией под dpi (гибко, дороже на железе)

Решение откладывается до первого реального экрана на прототипе.

## Уровни API

Три уровня — не стек, а три двери к одному framebuffer:

```
L3  UI редактор
    drag & drop, скрипты, live preview
    генерирует L2 под капотом

L2  Layer protocol  ← основной протокол
    PUT /config     — JSON со сценами и слоями
    PATCH /vars     — обновить переменные
    POST /scene/next — переключить сцену

L1  Raw pixel protocol  ← шунт, bypasses рендерер
    set pixel(x,y,color)
    fill rect(x,y,w,h,color)
    flush
```

L1 и L2 не иерархия — L2 не строится поверх L1. Оба пишут во framebuffer напрямую, просто разными путями. L1 — отдельный режим: пока активен, рендерер отступает и отдаёт framebuffer внешнему клиенту.

Приоритет реализации: L2 → L1 → L3.

---

## Транспорты

Один и тот же протокол поверх разных транспортов:

| Транспорт | Роль |
|---|---|
| **USB/UART** | Прототип и отладка; надёжен до настройки Wi-Fi; удобен для L1 |
| **Wi-Fi HTTP** | Основной транспорт; редактор работает из браузера; WebSocket для live sync |
| **BLE** | Онбординг: подключился, настроил Wi-Fi, дальше HTTP; не для стриминга кадров |

BT не основной транспорт для рендера — пропускная способность BLE не та.

## Где выполняется логика

Устройство — умное, работает без ПК. Это принципиальное решение:

```
DataSources на плате  →  плата сама тянет HTTP (погода, Spotify)
Агент на ПК юзера     →  отправляет локальные метрики (CPU, RAM)
                          POST /vars  {"system.cpu": 42}
Плата                 →  не знает что это CPU, просто кладёт в Variables
```

Загрузка CPU — не особый случай, а просто ещё один DataSource. Агент на ПК юзера шлёт данные, плата рендерит. Архитектура не меняется.

## Прототип — план

**Цель первого прототипа:** проверить петлю `данные → рендер → экран` на реальном железе.

### Железо
ESP32 + дисплей через SPI. ESP32 выбран потому что Wi-Fi добавляется позже без замены платы.

### Что делает ESP32
```
1. Читает JSON из UART
2. Десериализует через serde
3. Рендерит framebuffer
4. Выводит на дисплей через SPI
```

### Что делает ПК
```python
import serial, json

scene = {
  "layers": [{
    "type": "text",
    "source": { "static": "Hello" },
    "transform": { "x": 10, "y": 20 },
    "style": { "fontSize": 16, "color": "#ffffff" }
  }]
}

ser = serial.Serial('/dev/ttyUSB0', 115200)
ser.write(json.dumps(scene).encode() + b'\n')
```

Меняешь JSON → перезапускаешь скрипт → видишь на экране. Никакого веб-редактора пока.

### Что проверяет прототип
- Десериализация JSON в реальных условиях памяти ESP32
- Скорость рендера — успевает ли плата без артефактов
- SPI протокол с конкретным дисплеем
- Насколько удобна модель слоёв когда пишешь её руками

### Порядок шагов
1. `core` крейт — `no_std + alloc`, структуры слоёв, рендер в буфер; тесты на десктопе
2. ESP32 + UART: принять JSON, отрендерить, вывести на дисплей
3. Wi-Fi транспорт вместо UART
4. Веб-редактор как standalone с live preview через WebSocket
