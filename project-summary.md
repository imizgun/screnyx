# Умный дисплей — выжимка архитектурных решений

## Идея и позиционирование

Кастомный информационный дисплей с открытой экосистемой. Главный девиз — **свобода**: пользователь сам выбирает эстетику (пиксельную, минималистичную, насыщенную), сам собирает экран из готовых объектов как в Фотошопе, и при желании пишет скрипты.

Ниша: между закрытым Divoom/Pixoo (мало свободы) и AWTRIX (много свободы, но спартанский UI). Уникальность — **визуальный редактор**, которого нет ни у кого.

Сценарии, на которые ориентируемся: now playing (название, обложка, FFT-визуализатор), статистика Twitch, погода, пиксельные анимации в духе Divoom, системные метрики. Экран стоит рядом с ПК как украшение.

---

## Железо

| Решение | Обоснование |
|---|---|
| **Обычный IPS/OLED дисплей**, не LED матрица | Пиксельную эстетику можно сделать программно; обратное невозможно |
| **ESP32-S3** как основа | Устройство — только рендерер, Linux и JS-рантайм не нужны; Wi-Fi есть на борту |
| ILI9341 320×240 по SPI | Текущий прототип |
| Raspberry Pi Zero 2W | Рассматривался ради QuickJS и HTTP стека; после переноса логики в компаньон не обязателен |

Форм-фактор: квадратный или широкоформатный (не вытянутый), больше Pixoo Max по диагонали.

---

## Прошивка

**Язык: Rust**, `no_std`

- Рендерер — горячий путь, Rust исключает buffer overflow на этапе компиляции
- `embassy-rs` даёт async/await на bare metal без OS
- `serde` + `#[derive(Deserialize)]` — парсинг и валидация JSON бесплатно
- `core` крейт (типы, рендерер) тестируется на десктопе через `cargo test`, рендер в PNG, и компилируется в WASM для превью в редакторе

**Структура крейтов:**
```
core/            — типы, рендерер, интерполятор (платформонезависимо, no_std)
data_receivers/  — транспорты (UART, позже Wi-Fi)
screnyx/         — прошивка: core + HAL + дисплей
web/             — wasm-bindgen обёртка над core для редактора
```

## Архитектура системы

**Сцена живёт на устройстве, данные — в компаньоне.**

```
┌──────────── Компаньон (ПК) ────────────┐        ┌──────── Устройство ────────┐
│ Редактор (веб-UI, WASM превью)         │ scene  │ Scene (во flash)           │
│ DataSources: MPRIS+FFT, Twitch, погода,│ ─────► │ Assets (картинки, спрайты) │
│              CPU, HTTP, скрипты        │ vars   │ Variables (+TTL)           │
│                                        │ ─────► │ Рендерер + часы анимаций   │
└────────────────────────────────────────┘        └────────────────────────────┘
```

**Устройство — только рендерер.** Хранит сцену и ассеты, принимает переменные, рисует. Само ничего из сети не тянет: OAuth, API-ключи, TLS и разбор произвольных API на `no_std` — дорого, а каждый новый сервис требовал бы перепрошивки.

**Устройство — не зеркало.** ПК не передаёт пиксели, а передаёт смысл. Анимации, часы, статичные картинки работают на устройстве и без ПК. Пропускная способность это подтверждает: полный кадр 320×240 RGB565 = 153.6 KB — по UART 115200 это 13 секунд, а 32 полосы спектра — 32 байта на кадр.

**Компаньон — всё про внешний мир.** Ходит в API, считает FFT с цифрового звука, качает и ужимает обложки, выполняет пользовательские скрипты, раздаёт редактор. Сейчас работает на ПК, позже (с Wi-Fi) может жить на домашнем сервере или телефоне — протокол не меняется.

Устройство — не браузер. Это **template renderer**: цикл который подставляет переменные в шаблон, вычисляет трансформы и анимации, рисует в буфер. Принципиально проще браузера — нет DOM, нет reflow, нет layout engine.

## Модель данных

### Иерархия
```
Screen
  └── Scene  (набор слоёв + правила переключения)
        └── Layer  (Text | Image | Sprite | Bars | Shape)
              ├── Transform  (x, y, w, h, opacity, scale, z)
              ├── Source     (static | binding | template)
              └── Animation  (keyframes на любое свойство)

Assets     — картинки и спрайты, хранятся на устройстве по id
Variables  — заполняются компаньоном, доступны слоям через {{name}}
```

### Переменные
Типы: `string`, `number`, `array` (например полосы спектра), `asset` (ссылка на картинку).

У каждой переменной есть **TTL**. Если значение не обновлялось дольше TTL, слой переходит в «устаревшее» состояние (гаснет, показывает fallback). Выключенный ПК не ломает экран — пропадают только данные.

Время синхронизируется компаньоном при подключении, дальше устройство считает его само.

### Атомы на разных уровнях
- **Для пользователя** → Layer (высокоуровневый объект, как в Фотошопе)
- **Для рендерера** → Pixel в буфере
- Layer — это абстракция; рендерер внутри всё равно работает с пикселями

## Типы слоёв

Фиксированный словарь, покрывающий целевые сценарии:

| Тип | Описание | Примеры |
|---|---|---|
| **Text** | Строка, шрифт (встроенные bitmap шрифты с кириллицей), overflow: clip/scroll/wrap | название трека, зрители, температура, часы |
| **Image** | Asset или binding; целочисленный scale без сглаживания | обложка, аватар, иконка погоды, фон |
| **Sprite** | Кадры + fps + loop | пиксельные анимации, анимированные иконки |
| **Bars** | Массив → столбики; decay, peak hold, градиент, зеркальность | FFT спектр, история зрителей, почасовой прогноз |
| **Shape** | Прямоугольник, круг, линия, progress; параметры через переменные | прогресс трека, цель сбора, декор |

Спектр — не отдельный тип, а `Bars`: тот же слой рисует графики. Пиксельная эстетика — `Image`/`Sprite` с целочисленным масштабом: рисуешь 32×24, на экране ×10.

### Source на слое
```json
{ "static": "Hello" }
{ "binding": "track.title" }
{ "template": "{{artist}} — {{title}}" }
```

Слои только читают Variables — сами ничего не тянут. Рендерер работает синхронно.

### Пример: now playing
```json
{"layers":[
  {"type":"image","rect":[8,8,120,120],"source":{"binding":"track.cover"}},
  {"type":"text","rect":[140,16,172,20],"source":{"binding":"track.title"},"font":"m","overflow":"scroll"},
  {"type":"text","rect":[140,40,172,16],"source":{"binding":"track.artist"},"font":"s"},
  {"type":"bars","rect":[0,150,320,90],"source":{"binding":"audio.bands"},
   "bars":32,"gap":2,"gradient":["#00ffaa","#ff0066"],"decay":0.85,"peak_hold":true}
]}
```

## Анимация

Keyframes с нормализованным временем `t: 0..1`. Easing задаётся на каждом keyframe отдельно и описывает кривую до следующей точки.

Анимируемые свойства: `opacity`, `transform.x/y/scale`.

Триггеры:
- `onEnter` — при входе в сцену
- `onExit` — при выходе
- `onDataChange` — когда изменилась переменная в source
- `always` — каждый кадр

`duration` и keyframes разделены — скорость меняется одним полем, пропорции сохраняются.

Анимации считаются на устройстве и не зависят от компаньона.

## Скрипты

**Скрипты выполняются в компаньоне, не на устройстве.** QuickJS на устройстве не нужен.

- На ПК скриптовать бесплатно (JS, Python) — нет ограничений памяти, есть сеть и любые библиотеки
- Скрипт — это пользовательский DataSource: что-то считает и пишет переменные
- На устройство приходит только результат — переменные, которые рисуют обычные слои

Если нужно совсем произвольное рисование — L1 `BLIT` в регион.

## Редактор

- Раздаётся компаньоном, открывается в браузере
- Базово: drag & drop (Layer как объект с ручками)
- При необходимости: встроенный код-редактор для скриптов-источников
- Разрешение экрана берётся из манифеста устройства

### Превью через WASM

В WASM компилируется не прошивка, а крейт `core` — рендерер без зависимостей от железа:

```
screnyx (прошивка) = core + esp-hal + SPI/UART
web     (редактор) = core + wasm-bindgen + <canvas>
```

`core` рисует сцену в `&mut [u16]` (RGB565, w×h). На устройстве буфер уходит по SPI, в браузере — в `<canvas>` через `ImageData` (RGB565 → RGBA).

```
┌─ редактор (JS) ───────────────────────────┐
│  SVG-оверлей: рамки, ручки, drag         │ ← мышь
│  ───────────────────────────────────────  │
│  <canvas w×h, увеличен, pixelated>        │ ← пиксели из core.wasm
└───────────────────────────────────────────┘
```

Canvas только показывает результат рендера. Интерактивность — HTML/SVG оверлей редактора: тянешь ручку → редактор меняет `rect` в JSON → `core.render(scene)` → canvas обновился. Превью совпадает с экраном пиксель в пиксель: те же шрифты, обрезка, скролл.

Требование: `core` никогда не зависит от `esp-hal`.

## Абстракция экрана

**Принцип: любой дисплей, только зная его размеры.**

Для рендерера `core` экран — это просто плоский буфер. Всё что связано с физическим выводом — в прошивке. Рендереру всё равно какой интерфейс используется.

### Device manifest

При подключении устройство отдаёт манифест — редактор читает его и подстраивает canvas:

```json
{
  "device": {
    "name": "my-display",
    "firmware": "0.1.0",
    "screen": {
      "w": 320,
      "h": 240,
      "dpi": 133,
      "interface": "spi"
    }
  }
}
```

Поле `interface` — `"spi"` | `"rgb_parallel"` | `"mipi_dsi"`. Редактор это поле не видит и не использует.

Все координаты в JSON конфиге — в реальных пикселях экрана. Никакой нормализации и процентов: что видишь в редакторе, то и на экране.

### Отрисовка

- Не попиксельно: `Pixel.draw` выставляет окно адреса ILI9341 на каждый пиксель
- Регион слоя рендерится в буфер в RAM и отправляется одним `draw_raw_slice` (регион 320×90 = 57.6 KB, ~11 мс по SPI 40 МГц)
- Dirty regions: спектр перерисовывается каждый кадр, текст при скролле, обложка раз за трек; полный framebuffer пока не нужен

### Шрифты

Названия треков часто на кириллице — `embedded-graphics` mono fonts её не умеют, нужен `u8g2-fonts` (Unicode).

Открытый вопрос — dpi: 320×240 на 2" и на 5" дают очень разный результат для bitmap шрифтов. Решение откладывается до выбора финального экрана.

## Уровни API

Три уровня — не стек, а три двери к одному буферу:

```
L3  UI редактор
    drag & drop, скрипты, WASM превью
    генерирует L2 под капотом

L2  Layer protocol  ← основной протокол
    PUT scene   — JSON со сценами и слоями (сохраняется во flash)
    PUT asset   — бинарный блок картинки/спрайта
    SET var     — обновить переменную (JSON или бинарный массив)

L1  Raw pixel protocol  ← шунт
    BLIT x y w h <rgb565…>
```

L1 и L2 не иерархия — L2 не строится поверх L1. Оба пишут в буфер напрямую, просто разными путями.

Фрейминг: сцена и простые переменные — JSON, ассеты и частые массивы — бинарные пакеты `[type:u8][len:u16][payload]`. Текстовые строки на картинках и 60 Hz массивах захлебнутся.

## Транспорты

Один и тот же протокол поверх разных транспортов:

| Транспорт | Роль |
|---|---|
| **USB/UART** | Прототип; связь с компаньоном на ПК |
| **Wi-Fi** | Компаньон может жить не на ПК; WebSocket для live sync |
| **BLE** | Онбординг: подключился, настроил Wi-Fi |

Бюджет UART 115200 (~11.5 KB/s): спектр 32 полосы × 30 fps ≈ 1 KB/s, обложка 120×120 RGB565 = 28.8 KB ≈ 2.5 с раз за трек — влезает.

## Где выполняется логика

| Где | Что |
|---|---|
| **Устройство** | сцена, ассеты, переменные, рендер, анимации, часы |
| **Компаньон** | все DataSources, скрипты, редактор |

```
Компаньон  →  MPRIS: title, artist, artUrl → обложка ужата до RGB565
           →  FFT цифрового звука (cava raw / numpy) → audio.bands
           →  Twitch API, погода, CPU/RAM
           →  SET var {"track.title": "..."}
Устройство →  не знает что это трек, просто кладёт в Variables
```

Источник переменной — не особый случай, а просто ещё один DataSource компаньона. Архитектура устройства не меняется.

## План

**Цель:** петля `данные → рендер → экран` на сценарии now playing.

1. **`core`** — `Scene` / `Layer` / `Variable` / `Asset`, рендер слоя в буфер региона; тесты на десктопе с выводом в PNG
2. **Прошивка** — протокол `PUT scene` / `PUT asset` / `SET var` поверх UART с бинарным фреймингом; отрисовка регионами
3. **Компаньон** — один источник (MPRIS + cava), сцена руками в JSON
4. **Редактор** — `web` крейт (core → WASM), canvas + SVG оверлей
5. Wi-Fi транспорт
